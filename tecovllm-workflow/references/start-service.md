# 启动模型服务

## 选参考脚本

1. 优先复用用户指定的启动脚本或命令。需要改参数时，将脚本复制到本次任务目录。用户指定对照项时，只改对应选项和本次运行需要的卡、端口、日志路径。
2. 从历史挑脚本时，核对平台、实际权重目录和量化版本、目标容器的 vLLM 与 Python 入口，以及本次用途和选项。同一个模型可分别有 MTP 开关、`FULL_AND_PIECEWISE` 和 `FULL_DECODE_ONLY`、纯文本和多模态等脚本。按平台和场景选择匹配的参数、环境变量及 JSON 配置。
3. 缺少合适参考时，以本次要求和容器内 `vllm serve --help` 为准。模型权重、并行方式或场景选项仍有多个可行值时，先确认会影响结果的差异。MTP、Graph、量化、KV cache、parser、profiler 等参数跟随本次配置。

## 按用途选择服务

- 为第 4、5 步准备普通服务时，从参考命令移除 `--profiler-config` 及其等号或点分形式，关闭该版本的 profiler 与 size dump 设置。若脚本通过 `--config` 加载配置，核对其中的 `profiler_config` 和相关环境变量。
- 复用现有服务前，核对监听端口对应的进程、实际启动命令或可确认归属的启动记录。查到 profiler 配置或无法确认时，先取得可验证的普通服务，再执行第 4、5 步。若任务也包含起服务，按本次参数启动普通实例。
- T100 的第 6 步使用 dump size 服务，第 7 步使用 prof 服务。各自使用独立的启动脚本、端口和输出目录，保留本次模型、权重和并行设置。

## 写脚本

把模型路径、端口、可见卡、并行参数写在脚本里。用 `remote-dev` 的 `bash -ic` 进入容器并沿用已经初始化的环境。参考脚本依赖特定解释器或环境变量时，保留已核实的设置。对照场景每组一份脚本，便于直接看出命令差异。

下面是 T100 上同节点客户端的最小形态。将示例值替换成已核对的模型、卡、端口和并行配置。

```bash
#!/usr/bin/env bash
set -e

export SDAA_VISIBLE_DEVICES=0,1,2,3

exec vllm serve /path/to/model \
  --served-model-name model-name \
  --host 127.0.0.1 \
  --port 8030 \
  --tensor-parallel-size 4
```

H100 使用镜像里的 vLLM 入口。需要显式限制可见卡时，将示例中的设备设置行换为 `export CUDA_VISIBLE_DEVICES=0,1,2,3`，取值按容器实际 CUDA 逻辑编号或 GPU UUID。保留 H100 参考中已核对的 CUDA 和 vLLM 参数。

脚本只保留环境设置和启动命令。日志重定向和就绪检查放在启动脚本之外。写完执行 `bash -n serve.sh`，并核对容器内实际入口支持的参数。

## 运行和验收

1. 核对节点、容器状态、实际 Python/vLLM 入口、模型挂载和卡占用。T100 核对 `SDAA_VISIBLE_DEVICES`，H100 核对容器 GPU 映射及 `CUDA_VISIBLE_DEVICES`。确认可见卡与模型并行配置一致。按容器网络模式检查端口，`--network=host` 的容器查宿主端口。确认客户端所在位置能访问计划使用的地址。
2. 用 `remote-dev` 进入容器，从本次挂载的任务目录启动。前台 `serve.sh` 用下面的方式后台运行，并记录 PID 和日志路径。直接复用已经负责后台运行的脚本时，沿用它的启动方式和日志。

   ```bash
   nohup bash ./serve.sh > ./serve.log 2>&1 < /dev/null &
   printf 'PID=%s\n' "$!"
   ```

3. 查看本次进程和日志，从客户端可访问的位置轮询 `/v1/models`，确认返回预期的模型 ID。需要验证模型能力时，单独发一条符合场景的请求，多模态场景用图文输入。启动失败时保留服务日志和实际退出状态。
4. 交付节点、容器、脚本和日志的容器内及宿主路径、PID、服务地址、`served-model-name`、物理卡和逻辑设备编号。将已验收的服务地址和模型名交给后续测试阶段。
