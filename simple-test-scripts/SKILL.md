# 简洁模型服务与测试脚本

目标：交付用户一眼能看懂、可以直接运行和修改的脚本。用户指定的测试仓库、原生入口、参考命令和统计口径优先；不要把一个命令改造成一套框架。

## 适用的三类脚本

### 模型服务端启动脚本

- 直接展示 `vllm serve ...` 等原生启动命令，保留参考脚本的参数名称、参数值和命令结构，只调整用户要求的部分。
- 环境激活、可见卡、模型路径、端口和服务日志路径应容易找到；不要藏进多层函数、命令生成器、参数字典或调度器中。
- 开关对照只改变对应参数。例如开 MTP 版增加 speculative-config，关闭版不传；不要同时改 dtype、KV cache、EP、编译、缓存或 batch 设置。
- 服务端脚本只负责启动服务和保存服务日志，除非用户要求，不附带客户端测试、自动停服、重启或队列管理。

### 测试客户端脚本

- 功能验证、文本/图像请求、精度评测等，优先使用用户给出的原生客户端命令；已有评测脚本时直接运行，不另写 HTTP 客户端或包装测试类。
- 服务地址、served-model-name、请求内容、数据集和结果目录按任务对齐。必要的单次 `curl` 验证应直接展示请求，不扩展为通用请求框架。
- 客户端负责发送请求或运行评测，不顺带修改服务配置、安装环境或启停模型服务；这些动作只有用户要求时才加入。

### 性能测试脚本

- 直接使用指定测试库的性能入口，用少量循环表达输入长度、输出长度、BS、请求数或图像尺寸组合。
- 预热次数、正式轮次、记录哪一轮由用户决定，日志与原生结果保存在清楚的目录中。
- 不自行增加 profiler、metrics 采集、缓存控制、计时或指标计算；用户明确要求时，仅添加完成该要求的必要命令。

三类脚本共享以下规则。用户只要求其中一类时，不额外交付其他类别；要求服务端与客户端配套时，核对地址、端口、模型名称与功能开关一致，不因此增加统一控制器。

## 先找到已有入口

- 阅读用户给出的参考脚本，定位指定仓库真正提供的 CLI，核对需要的参数。
- 工具已经支持所需测试时，直接执行其入口，例如 `python vllm_requests.py ...`。仅仅使用了同一个仓库中的类，不等于遵守了“直接用这个脚本测试”。
- 在参考脚本上做必要修改：模型、路径、端口、设备、输入输出长度、并发、请求数、用户要求的功能开关。
- 不为了沿用自己之前写的适配器，绕开用户新指定的仓库或参考脚本。

## 脚本默认形态

- 环境初始化 → 工作目录 → 必要的目录创建 → 原生命令；多组用例只增加直白的 `for` 循环。
- 固定参数直接写在命令中。变量用于实际变化或反复使用的值，例如输入长度、BS、输出目录；不把所有参数都变成环境变量或函数参数。
- 服务脚本把完整启动命令放在显眼的位置。用户要两份开关对照脚本时，允许少量重复，优先让差异直接可见。
- 客户端直接运行测试仓库的脚本。不额外写 Python 包装器、动态导入、继承测试类、`exec` 源码或运行时替换代码。
- 日志只保留任务需要的内容：服务日志、客户端日志和工具原生结果。没有要求时，不创建控制器、事件系统、状态 JSON、哈希清单、自动报告或结果校验框架。
- 失败时保留原始错误。简单退出或继续下一组，按用户要求及参考脚本决定；不擅自增加重试、降级或切换实现。

## 提测基准精度测试脚本

- 用户要求精度提测、沿用提测基准或对齐已确认的精度客户端时，先读 [提测基准与环境准备](references/precision-submission-baseline.md)，以 [提测基准精度测试脚本](assets/precision_submission_baseline.sh) 为参考，再按本次模型、地址和目录作必要调整。
- 本基准直接运行原生 `vllm_precision.py`，同一个服务上依次执行 LongBench v2、ToolBench、MVBench；不额外传并发、输出上限、模型类型或样本上限，不为对齐日志名而修改测试库默认值或新增 CLI 参数。用户当前另有要求时，以当前要求为准。
- 精度提测默认使用 `http://10.10.30.109/tecoap/teco-modeltest.git` 的 `vllm` 分支。实际测试前获取该分支最新 commit，核对该版本的入口和依赖，记录实际 commit；客户端指向本次检出的仓库。已有本地修改时保留原目录，另建干净 checkout，具体步骤见配套说明。
- 实际精度评测前，按本次 teco-modeltest checkout 的依赖声明准备独立 Python 3.12 Conda 环境，不再固定 EvalScope 1.8.1。环境名包含框架版本，例如仓库要求 `evalscope==1.11.1` 时使用 `evalscope_py312_1_11_1`；pip 安装优先使用清华源 `https://pypi.tuna.tsinghua.edu.cn/simple`；安装范围与版本核对见配套说明。评测环境与模型推理环境分开。
- 三条评测命令在脚本内依次等待；后台运行时用 `nohup` 启动整份脚本，不给单项命令加 `&`。只要求写脚本或更新 skill 时，不实际 clone、更新工作仓库、安装环境、启动模型或评测。

## 不改变实验含义

- 测什么、跑几次、是否预热、取哪一轮、是否并行，以用户当前要求为准。不要把某次任务中的“预热一次取第二轮”固化为所有测试的规则。
- 使用原生工具的输入生成、随机种子、采样、输出处理、计时和统计逻辑。不要默默修正流式 token 计数、修改超时、强制固定种子或更改指标公式。
- 不擅自清空缓存、关闭 prefix cache、调用健康/metrics/profile 等接口、改服务调度参数或增加环境变量。用户要求、参考脚本已有且适用于当前任务的行为可以保留。
- 如果原生工具存在会影响本次结论的具体问题，简短指出问题和影响，提出最小修复。不要暗中包裹或替换实现，也不要将已知无效的结果称为有效对比。
- “创建脚本”“先给我看看”只授权准备文件；不启动服务、占卡或发送测试请求。用户要求运行时，才在既有授权范围内执行。
- 用户只要求完善 skill 时，不触碰已有测试脚本、服务、队列或性能任务。

## 验证与交付

- 先用 `bash -n` 等静态检查确认语法，并对照仓库参数定义核对命令。用户要求先检查时，不通过运行测试来验证脚本。
- 检查每项新增行为是否必要：删掉它还能满足用户要求，就删掉；确有必要则用最少代码实现并说明原因。
- 最后给脚本绝对路径、简短用法及是否执行过。不要用大段工程说明掩盖复杂实现。

## 正反例

用户要求：“用指定 teco-modeltest 仓库测 1K、4K，BS 为 1、32，输出 1024。”

优先采用：

```bash
cd /path/to/teco-modeltest/lm_infer/unit
for INPUT in 1024 4096; do
  for BS in 1 32; do
    python vllm_requests.py \
      --server_ip_port 127.0.0.1:8030 \
      --model_name Qwen3.6-35B-A3B \
      --tokenizer_path /path/to/model \
      --model_type llm --batch "$BS" --request_nums "$BS" \
      --seqlen "$INPUT,1024" \
      --output_dir "out/in${INPUT}_bs${BS}"
  done
done
```

避免采用：新增 `modeltest_case.py` 动态载入源文件、改流式读取和统计公式，再由 shell 调用它，附带缓存重置、token 校验和状态管理。即使它复用了仓库代码，也超出了“直接运行原生测试脚本”的要求。
