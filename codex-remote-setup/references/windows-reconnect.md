# Windows 桌面端启动重连

仅在用户要求排查本机 Codex/ChatGPT 桌面端时使用。远程 SSH 配置不需要自动执行本节。

## 先确定失败入口

核对本次桌面进程、聊天 ID 和时间范围的日志，区分 `os error 10054`、SSE 空闲超时和鉴权失败。模型 WebSocket 与远程控制 WebSocket 是不同连接，不把其他聊天或旧进程的错误算作本次失败。若 WebSocket 失败后出现 `falling back to HTTP`，只能说明 HTTP 回退可用，不能说 WebSocket 重试成功。

比较直连和经实际本地 HTTP 代理的 TLS/Upgrade 路径。不带凭据的 HTTP 401 只证明到达认证关卡。然后用实际入口的既有登录做小型模型请求，确认所用传输、重连数和结果；不复制或输出登录令牌。

## 保留原供应商，验证显式代理

Windows 系统代理设置不保证每种原生连接都采用代理。先在测试子进程中设置 `HTTPS_PROXY` 为已验证的本地 HTTP 代理地址，保留原模型和供应商。验证内置 `openai` 的 WebSocket 是否通过该代理完成真实请求，避免先更换供应商或关闭 WebSocket。

若显式代理验证成功，在本机修复的授权范围内选择持久化方式：

- 仅让 Codex 使用代理时，在它的启动入口设置环境。
- 使用 Windows 当前用户的 `HTTPS_PROXY` 时，先备份原值，检查是否与现有代理冲突，再保存。这个设置也会影响该用户其他继承此环境的 HTTPS 工具；使用实际端口，不把示例 `10808` 当作所有机器的配置。

保存用户级变量后通知 Windows 环境变化。已有桌面、终端和后台进程不会自动继承新值；完全退出目标桌面程序后，从能继承新环境的入口启动。不能把“注册表已保存”当作“运行中的进程已采用代理”的证据。

## 恢复旧聊天也要验证

供应商 ID 是实际选择依据，例如 `openai` 与 `OpenAI` 是不同 ID。`supports_websockets=false` 只作用于选中的供应商；已有聊天可能保存并继续使用原供应商。只修改自定义供应商并验证一个新 CLI 会话，不能证明恢复的桌面聊天已经修复。

不要直接改聊天数据库来强行切换供应商。若此前添加了无效的供应商切换作为临时绕行，先备份，再仅撤回此次添加的设置，保留用户其他配置。

修复完成的证据必须包括重启后原聊天的真实请求和新进程日志：确认没有对应的 WebSocket 连接错误或重试，并确认是否发生 HTTP 回退。独立 CLI 测试通过时，只报告 CLI 的结果；桌面验证未完成就明确说明。
